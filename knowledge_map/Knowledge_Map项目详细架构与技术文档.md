# Knowledge_Map 项目技术梳理与说明文档

## 一、 项目定位
**Knowledge_Map** 是一个用 **FastAPI** 编写的后端服务，主要用来“提取和解析文档信息”。
它的核心作用就是把我们常见的各种文档（比如扫描版 PDF、文字版 PDF、docx 文件、TXT 文件），统一转换成一种格式固定、内容结构化的 JSON 数据。
这样一来，后续不管团队是要搭建“知识图谱”，还是要把数据喂给“大模型（LLM）”来做问答，都有标准数据可用。
此个系统既包含传统的纯文本抽取工具，也集成AI视觉分析模型——Dolphin-V2，用来专门处理排版复杂、或者是由图片拼成的扫描版文档。

## 二、 环境部署与启动指南

### 1. 基础环境与依赖
根目录下的 requirements.txt 包含了项目所需的所有依赖。

### 2. Dolphin-V2 模型的下载与配置
由于 Dolphin 模型体积庞大，代码仓库中并未直接包含其权重文件。如果缺少模型，服务在启动时会直接报错。
获取模型：请前往 HuggingFace 下载 Dolphin-V2 模型的完整权重文件。
放置路径：默认情况下，需要将下载好的模型文件夹放置在：
algorithm/Dolphin/hf_model/ 目录下。
也可以自定义路径：如果你的服务器中已有模型，或者你想放在其他硬盘，请打开代码中的 global_config_variable.py，修改其中的常量 DOLPHIN_MODEL_PATH 指向你的实际绝对路径。

### 3. 启动服务
在终端首先激活环境: conda activate dolphin
再启动服务:python app.py
在终端中看到如 [INFO] Dolphin model loaded. [INFO] Application startup complete 与 [INFO] Uvicorn running on http://0.0.0.0:8000 时，说明项目成功启动。

### 4. 自行测试接口

请求地址: `http://127.0.0.1:8000/api/file/parse`

请求格式样例:

## 三、 代码结构的划分

为了能快速看懂代码并在以后做好维护，整个项目代码大概分了四个主要部分：

### 1. 服务的入口
- **主要文件**: `app.py`
- **主要工作**: 
  - 这是整个程序的起点，负责启动和管理 Web 服务。
  - 在服务刚启动的时候，它会提前加载好 Dolphin-V2 模型。这样等用户第一次传文件时，就不会因临时加载模型而再消耗时间。
  - 设定文件存放和下载的地址。比如文件解析成功后，可以直接通过一条 URL 网址链接把结果下载下来。


### 2. API 接口层
- **主要文件**: `api/fileParser.py`
- **主要工作**:
  - **异步操作**：提供 `POST /api/file/parse` 接口。为了防止大文件解析或 AI 视觉推断导致网络请求超时，系统采用了异步操作。接收到请求后会立刻向前端返回一个 `taskId`（表示任务已受理），而实际的下载和解析流程则在后台静默运行，随后可通过查询接口获取结果进度。
  - **多文件并发与线程隔离**：当单次传入多个文件时，代码会利用异步机制（`asyncio`）同时发起处理；对于下载文件、跑 AI 模型的工作，系统会将其放到独立的后台线程池（`to_thread`）中执行，确保主 Web 服务的并发响应能力不受影响。
  - **限制并发排队**：虽然支持异步并发，但为了保护系统硬件，设定了“信号量（Semaphore）”控制，当前同时只能有 5 个文件处于“正在解析运算”的状态。这主要是防止瞬间涌入太多耗资源的任务，导致服务器 CPU 跑满或 GPU 显存爆掉引发宕机。
  - **智能分发任务（路由）**：接到文件后自动研判类型，.txt 和 .docx 直接分发给对应模块；若是 PDF，则会先尝试读取头 2 页的字数含量，推断其是“纯文本排版”还是“按图扫描的版面”，从而精准丢给普通抽字模块或 Dolphin-V2 模型处理。
  - **数据标准化打包**：不管底层各个模块是用什么方式解出了怎样的数据，最后都在这里进行统一清洗，拼凑成格式完全一样的数据包（必须包含段落 `page_texts`、供大模型一口吞的 `full_text` 以及异常警告 `warnings` 等），最后打包出去。


### 3. 具体工作的解析器（核心算法区）
这里是项目的核心大脑，里面放了不同的小模块，各司其职：
- **`algorithm/pdfAna/` (处理文字版 PDF)**
  - 使用 `PyMuPDF` 的工具库。
  - 能判断这页纸是否被分成了左右两栏，能顺着正常的阅读顺序把句子接起来，还能修补中文排版里的换行符。
- **`algorithm/Dolphin/` 和 `dolphinAdapter/` (处理扫描版 PDF)**
  - 也就是把 PDF 当成一张张带字的图片，然后拿 AI 模型去“看图识字”。
  - 它能用框框画出来：哪块是正文（Text）、哪行是大标题（Title）、哪里是一张图表（Figure）或者表格（Table）等元素。
  - Adapter 文件夹的作用，就是在拿到 AI 生成的结果之后，将杂乱的换行符号进行清洗，并转换为接口要求的标准统一格式。
- **`algorithm/txtAna/` 和 `algorithm/wordAna/` (处理txt文本和docx文档)**
  - 处理 TXT 文本时，会探测文件的字符编码（如尝试 UTF-8、GBK、BIG5 等）以避免中文乱码，同时能从文件名中推测作者信   息，最终将杂乱的换行进行统一整理，并转换为标准统一格式。
  - 处理 docx 文档时，会提取段落正文及文档元数据（如内置作者或从文件名推断出作者），并将提取结果转换为标准统一格式。


### 4. 其他配置与测试工具
- **`config/` 和 `values/` 目录**: 里面放了一些公用的变量和设置。
- **`mock_backend/`（模拟接收器）**: 这是自己开发测试用的,因为有些大文件解析可能要好几分钟，所以采用了异步机制,这个模块就是为了模拟“成功通知”的第三方系统。
- **`test/` 目录**: 里面放了一些测试文件和测试代码，用来验证解析器模块的正确性。

## 四、 一个文件传进来到出去，经历了什么流程？

大家如果想看懂代码里的业务逻辑，可以直接顺着这个流程看，非常清晰：

1. **收到请求**: 另一个系统调用 `/api/file/parse`，告诉我们需要解析文件的下载地址（URL）。
2. **下载**: 后端的代码会把这个文件下载到本地临时文件夹里，并检查它是个什么后缀的文件。
3. **路由分流**:
   - 发现是 `.txt` -> 传给算文本的代码(algorithm\txtAna\engine.py)。
   - 发现是 `.docx` -> 传给算 Word 的代码(algorithm\wordAna\engine.py)。
   - 发现是 `.pdf` -> 先调用detect_pdf_type函数读取PDF前两页，并提取页面中可复制的文本，剔除空格、换行，统计总字符数； 
     具体会根据下述阈值判断：•文本长度 ≥ 30 → 文字版 PDF  •	文本长度 < 30 → 扫描版 PDF  •  解析异常时，默认判定为扫描版。
4. **解析**:
   - 如果判断出 PDF 为文字版，就直接交给 `pdfAna` 模块解析。
   - 如果判断出 PDF 为扫描版，就使用 Dolphin-V2 模型解析。
5. **结果整合**: 经解析后，文件的数据格式会各有不同，最终会在 `api/fileParser.py` 包揽并整理成一模一样的格式。
6. **保存并返回网址**: 把整理完善的 JSON 数据存进 `results/` 文件夹下，然后把网址发给请求方。

## 五、 最终生成的标准数据格式

不管传进来的是扫描件还是 Word，从系统出去的数据统一都是这种 JSON 格式：

```json
{
  "filename": "测试示例文件.pdf",          // 传入的原文件名
  "author": "解析出的作者名",              // 尽可能解析出的作者（如果没有则为空字符串）
  "pages": 3,                             // 文档统计的总页数
  "pdf_type": "text",                     // 文档表现大类：'text' (纯文本/Word/文字版PDF) 或 'scan' (扫描版PDF)
  "engine": "dolphin",                       // 实际使用的底层解析引擎如：'txt', 'docx', 'pdf_text' 或 'dolphin'
  "page_texts": [                         // 按页拆分存放的段落数据列表
    {
      "page": 1,                          // 页码
      "text": "第一页经过清洗整合的正文内容...",
    }
  ],
  "full_text": "输入给模型/其他解析引擎的整篇文章...",
  "warnings": ["author_missing"],         // 质检警告（如缺失作者 missing_author, 有空页 empty_pages 等，正常则为空列表）
  "error": null,                          // 发生严重错误时会填入报错字符串，正常成功时为 null
  
  // ⚠ 特别说明：当引擎为 'dolphin' 时，会额外返回 'raw' 字段
  "raw": {                                
    "source_file": "...",                 // 提供 AI 模型输出的极其详细的版面源数据
    "total_pages": 3,                     // 文档统计的总页数
    "pages": [                            // 包含每个文本框的具体类型(para/list/header)以及坐标(bbox)
      // ... 
    ]
  }
}
```
